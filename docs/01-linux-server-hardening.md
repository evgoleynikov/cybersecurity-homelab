# 01. Развёртывание и базовая защита Linux-сервера

**Проект:** Cybersecurity Home Lab  
**Автор:** Evgeny Oleynikov  
**Дата выполнения:** ноябрь 2026 года  
**Статус:** базовое развёртывание и проверки завершены; мониторинг и публикация сайта запланированы

> **Примечание по безопасности.** В отчёте используются **условные IP-адреса** `192.168.10.10` (Ubuntu) и `192.168.10.20` (административный MacBook). В реальном стенде использовались другие адреса. Приватные ключи, пароли, MAC-адреса и идентификаторы оборудования не публикуются.

## 1. Цель и результат

**Цель:** развернуть Ubuntu Server в виртуальной машине на домашнем NAS, настроить удалённое администрирование, ограничить входящие сетевые подключения и запустить тестовый веб-сайт.

**Полученный результат:** Ubuntu Server установлена и доступна по SSH с MacBook; настроена аутентификация по ключу ED25519 без входа по паролю; брандмауэр UFW разрешает только необходимые подключения; Nginx отдаёт собственную HTML-страницу по HTTP в домашней сети.

Это **учебная лаборатория по администрированию и базовой защите**, а не результат аудита безопасности или доказательство полной защищённости сервера.

## 2. Инфраструктура и архитектура

| Компонент | Конфигурация и назначение |
|---|---|
| Физический хост | TerraMaster F2-425 Plus, TOS 7 |
| Хранилище | Существующий том Btrfs на RAID 1; отдельное хранилище ВМ `Lab-VMs` |
| Виртуализация | TerraMaster VMs, виртуальное оборудование QEMU |
| Виртуальная машина | `Ubuntu`: 2 vCPU, 2 ГБ RAM, виртуальный диск 40 ГБ |
| Гостевая ОС | Ubuntu Server 24.04.5 LTS, архитектура x86-64 |
| Сеть | Open vSwitch, внешняя виртуальная сеть `VM-LAN`, интерфейс Ubuntu `ens3`, DHCP |
| Администрирование | MacBook, OpenSSH, ключ ED25519 |
| Сетевой экран | UFW |
| Веб-сервер | Nginx, тестовая статическая HTML-страница |

```text
MacBook (администратор)
  │  SSH: TCP/22; HTTP: TCP/80
  ▼
Домашний маршрутизатор (DHCP-резервирование)
  │
  ▼
TerraMaster NAS — TOS 7 / Btrfs / Open vSwitch
  └── VM: Ubuntu Server (2 vCPU / 2 ГБ / 40 ГБ)
      ├── OpenSSH — доступ по ключу ED25519
      ├── UFW — фильтрация входящих соединений
      └── Nginx — локальная HTML-страница
```

Виртуальная машина имеет собственный сетевой интерфейс и IP-адрес. Физические диски NAS **не передавались** гостевой системе через PCI Passthrough: Ubuntu работает с отдельным виртуальным диском.

## 3. Развёртывание виртуальной машины

1. В TOS 7 проверил доступные ресурсы NAS, тип файловой системы Btrfs и работу приложения **VMs**.
2. Включил Open vSwitch и создал хранилище виртуальных машин `Lab-VMs` на существующем томе.
3. Создал ВМ с 2 vCPU, 2 ГБ RAM и виртуальным диском 40 ГБ; выбрал загрузку с ISO Ubuntu Server 24.04.5 LTS.
4. Создал внешнюю виртуальную сеть `VM-LAN` через физический интерфейс NAS, подключил к ней сетевой адаптер ВМ.
5. Установил Ubuntu на **виртуальный** диск с автоматической разметкой и LVM.
6. Проверил успешную загрузку установленной системы и вход под обычной учётной записью с правами `sudo`.

**Разметка:** отдельный `/boot` около 2 ГБ, корневой логический том `/` около 19 ГБ, остальное пространство оставлено свободным внутри группы LVM для возможного расширения. Используется файловая система ext4 в гостевой ОС.

**Сложность при установке:** первоначальная загрузка установщика останавливалась на системных сообщениях. После смены виртуального видеоадаптера с `vmvga` на `vga` установщик открылся, и установка завершилась. Связь причины и изменения следует считать практическим наблюдением, а не доказанным дефектом драйвера.

## 4. Проверка операционной системы и сети

Для инвентаризации системы использовал:

```bash
hostnamectl
ip link show ens3
```

**Подтверждено:** Ubuntu Server 24.04.5 LTS, ядро `6.8.0-149-generic`, архитектура `x86-64`, виртуальное оборудование QEMU. Фактическое имя узла при проверке — `buntu-lab` (небольшая опечатка в имени; исправление запланировано).

Сетевой интерфейс `ens3` получил адрес через DHCP. На домашнем маршрутизаторе выполнено резервирование адресов по MAC-адресам для Ubuntu, административного MacBook и NAS. Приватные адреса и MAC-адреса здесь намеренно не приводятся.

## 5. Защита удалённого доступа (OpenSSH)

### 5.1. Проверка подлинности сервера

При первом подключении с MacBook сверил отпечаток публичного ключа сервера с результатом команды на Ubuntu:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Только после совпадения отпечатков подтвердил доверие к узлу в SSH-клиенте.

### 5.2. Настройка доступа по ключу

На MacBook создана **отдельная** пара ключей ED25519 для лаборатории:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/ubuntu_lab_ed25519 -C "ubuntu-lab"
```

На сервер передан **только публичный** ключ и добавлен в `~/.ssh/authorized_keys`. Приватный ключ остался на MacBook и защищён парольной фразой.

В отдельном файле `/etc/ssh/sshd_config.d/01-lab-hardening.conf` заданы параметры:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

Синтаксис проверен командой `sudo sshd -t`, эффективные параметры — командой:

```bash
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication) '
```

**Фактический результат проверки:**

```text
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
```

После применения параметров проверил повторный вход по ключу с MacBook. Отдельная попытка подключения без публичного ключа завершилась ожидаемым отказом:

```text
Permission denied (publickey).
```

Это подтверждает, что тестовый клиент не смог войти по обычному SSH-паролю. Локальный пароль пользователя для `sudo` при этом сохранён.

### 5.3. Диагностика временного сбоя

При одной из первых попыток подключения SSH-соединение закрылось до авторизации (`Connection closed by ... port 22`). Проверил состояние службы через `systemctl status ssh`, её прослушивание порта 22 и журналы `journalctl`. Служба была активна; повторное подключение завершилось успешно. **Точная причина разового сбоя не установлена** — это отмечено как ограничение диагностики.

## 6. Настройка брандмауэра UFW

Брандмауэр установлен отдельно. Входящие соединения запрещены по умолчанию, исходящие разрешены. Для административного MacBook добавлены исключения для SSH и тестового HTTP.

Ниже — **пример команд с условным адресом MacBook**, не копия реальной адресации стенда:

```bash
sudo apt install ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.10.20 to any port 22 proto tcp
sudo ufw allow from 192.168.10.20 to any port 80 proto tcp
sudo ufw enable
sudo ufw status verbose
```

**Проверенное состояние:**

```text
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)

22/tcp  ALLOW IN  192.168.10.20
80/tcp  ALLOW IN  192.168.10.20
```

*Примечание:* последние два адреса в блоке выше обезличены. Реальные правила применены для адреса административного устройства.

После включения UFW новое SSH-подключение по ключу **успешно установлено**. Отдельного сетевого теста блокировки с другого устройства пока **не проводилось**: ограничение подтверждено конфигурацией, а не негативным тестом со стороннего IP.

## 7. Веб-сервер Nginx

Nginx установлен из репозиториев Ubuntu:

```bash
sudo apt install nginx
systemctl is-active nginx
```

**Результат:** `active`.

Затем стандартную страницу заменил собственной статической HTML-страницей лаборатории в каталоге `/var/www/html/`. При открытии тестового HTTP-адреса с MacBook страница **успешно отображается в браузере**. Это подтверждает работу цепочки: клиент → локальная сеть → правило UFW → Nginx → HTML.

**Важно:** на текущем этапе сайт доступен **только в домашней сети с разрешённого IP-адреса**. Публичный домен, HTTPS и внешний доступ ещё не настроены. Никаких портов домашнего NAS для общего доступа в интернет в рамках этой работы не открывалось.

## 8. Обновления и обслуживание

Выполнил:

```bash
sudo apt update
apt list --upgradable
sudo apt upgrade
```

Основная часть обновлений установлена. Три оставшихся пакета (`distro-info`, `python3-distro-info`, `snapd`) были отложены механизмом **phased updates** (на момент проверки — поэтапное распространение 10%). Принудительно обходить этот механизм не стал. Впоследствии при входе Ubuntu сообщила об отсутствии немедленно доступных обновлений.

Обновление сопровождалось перезапуском системных служб; после этого доступ по SSH и работа веб-сервера проверены повторно. Обновление дистрибутива до следующей LTS-версии в этой лабораторной не выполнялось.

## 10. Выводы и дальнейшие задачи

**Изучено и применено на практике:** виртуализация Linux на NAS, базовая настройка гостевой ОС, интерфейсы и DHCP, устройство SSH-аутентификации, проверка ключа хоста, ключи ED25519, параметры OpenSSH, принцип *deny by default*, правила UFW, работа Nginx и техническая диагностика.

**Что ещё необходимо сделать:**

- Проверить блокировку SSH и HTTP с другого устройства и сохранить обезличенные доказательства.
- Исправить опечатку в hostname с учётом зависимостей и проверить работу после изменения.
- Организовать резервное копирование и проверить восстановление тестовых файлов.
- Перенести исходный код страницы в GitHub, настроить контролируемое развёртывание изменений.
- Добавить HTTPS и безопасную схему публичной публикации портфолио, не открывая панель NAS и SSH всему интернету.
- Отдельным проектом развернуть сбор и анализ журналов безопасности (например, с Wazuh на более мощной машине).

> **Итог:** создан рабочий домашний Linux-стенд, в котором подтверждены базовые меры защиты удалённого администрирования и сетевой доступности веб-сервера. Следующие этапы направлены на повышение воспроизводимости, мониторинг и практические проверки защищённости.
